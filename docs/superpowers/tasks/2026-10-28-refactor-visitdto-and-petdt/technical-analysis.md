### Patterns and Conventions

- MapStruct config (`pom.xml`): `mapstruct` and `mapstruct-processor` 1.6.3 as compile dependencies; processor also on `annotationProcessorPaths` for `default-compile` only (not testCompile); compiler args `-Amapstruct.defaultComponentModel=spring`, `suppressGeneratorTimestamp`, `suppressGeneratorVersionInfoComment`. Mappers are interfaces with no `componentModel` attribute (global default applies); no `@MapperConfig`, no shared config.
- MapStruct 1.6.3 supports Java records natively (constructor-based mapping, accessors named like components); a record target uses the canonical constructor rather than setters, so nested-target `@Mapping(target="pet.id")` on a record source is fine, but `target="pet.id"` style on **entity** targets (Visit/Pet) is unaffected.
- Validation: Jakarta Bean Validation annotations on the generated getters/fields, plus custom `rest.validation.PetAgeValidation` / `PetAgeValidator` (rejects future birth dates and birth dates older than 50 years; null -> valid). Applied on the `birthDate` field via `x-field-extra-annotation`.
- Java style: 4-space indent; Javadoc `/** Map X & XDto using mapstruct */` on mappers.

## 6. Risk Indicators

- Generated source of truth: DTOs live in `target/` and are overwritten by every build; a records refactor cannot be done by editing them. The generator has no records option and no custom templates exist. Any approach (custom mustache templates via `templateDirectory`, replacing the generated models with hand-written classes plus `importMappings`/`typeMappings`/`schemaMappings` so the generated API interfaces reference them, or a post-generation step) is a build-design decision with the highest complexity in this task.
- Speculative: `VisitDto`/`PetDto` records would need `@JsonProperty`, `@Schema`, Bean Validation annotations and `@PetAgeValidation` preserved, or OpenAPI docs and 400 validation behaviour (via `ExceptionControllerAdvice`) would change.
- Speculative: records are immutable, so every `new PetDto()` plus fluent-setter chain in tests (`PetRestControllerV1Tests`, `OwnerRestControllerV1Tests`, `VisitRestControllerV1Tests`, `V2RestControllersTests`) and `PetDto.visits`/`addVisitsItem` usage would need rewriting. `OwnerDto` (generated, mutable) holds `List<PetDto>`, so mixed record/POJO DTOs would be needed.
- Speculative: compact-constructor validation duplicates Bean Validation; constructor exceptions during Jackson deserialization surface differently (message conversion failures) than `MethodArgumentNotValidException`, which may change error responses asserted by tests.
- Speculative: `PetDto.visits` has no setter initialization beyond `new ArrayList<>()`; records would have to defend against null lists.
- Circular `uses` between `PetMapper` and `VisitMapper`; MapStruct records use constructor injection of nested values, so generated code should be checked after compile.
- Java version mismatch: task says Java 21 but project compiles at release 17; whether to bump `java.version` is undecided.
- `mapstruct-processor` is on `annotationProcessorPaths` for `default-compile` only; test compilation does not run MapStruct (mappers are not generated in tests).
- No mapper unit tests and no guides/ADRs; behaviour changes would be caught only by controller tests.

## 7. Summary for Complexity Assessment

The Visit and Pet DTOs are produced by openapi-generator 7.25.0 (spring generator) from `src/main/resources/openapi.yml` into `target/generated-sources/openapi/.../rest/dto` and are consumed by 3 MapStruct mappers (Visit, Pet, Owner via nested `List<PetDto>`), 3 v1 controllers and 4 test classes (82 occurrences in 9 files). The project is spec-first, mutable POJOs with fluent setters; the generator version in use has no records option and the repo has no custom templates. The change surface therefore includes build configuration (templates or hand-written DTOs plus generator mappings), two or three mappers, controllers that call getters, and heavy rewriting of tests that rely on `new XDto().fluent()` construction.

Technical novelty is high for this codebase: nothing hand-written exists as a DTO, records are not used anywhere, Java 21 is not configured (release 17 inherited from Boot 4.1.1), and Jackson 3 plus MapStruct 1.6.3 interplay must be verified. MapStruct 1.6.3 itself supports records, so the mapper edits are modest; the generation strategy is the risk.

Test posture is moderate: controller-level MockMvc tests cover the endpoints and serialization, but there are no mapper or DTO validation unit tests, and JaCoCo gates (85% line, 66% branch) apply to hand-written code while `rest/dto` is excluded. Key risk factors are the generator limitation, immutable-record impact on tests, validation semantic differences, and the Java version setting.
